# Methodology

This document explains how **Ecommerce Decision Diagnosis — Case #1** was designed, measured, and interpreted. It focuses on analytical methodology and evidence boundaries rather than repeating the business narrative on the portfolio page.

> **Controlled simulation:** No real customer data is used in this case.

## 1. Case Design and Controlled Simulation

The case represents a newly launched, owner-operated U.S. ecommerce store selling Pilates and fitness accessories, with grip socks as the hero category.

The analytical scenario covers **90 days (May–July 2026)** and uses controlled synthetic behavioral and transaction data. The diagnostic workflow is:

**Business Question → Locate WHERE → Narrow the weak stage → Test explanations → Reject unsupported hypotheses → Identify the next measurement or decision**

The simulation was not designed by choosing a root cause first and manufacturing data to prove it. Business volumes and behavioral patterns were calibrated to plausible ecommerce ranges, while the analysis was allowed to produce weak, mixed, or rejected hypotheses.

The Shopify Dev Store contains the real Product / Variant implementation used for the case. Simulated Orders, Customers, Sessions, Funnel Events, Behavioral Pageviews, and Marketing Spend were **not generated by real Shopify customers and are not represented as Shopify transactional data**.

The case analysis also did **not** use GA4 as a data source.

## 3. Analytical Data Map and Grain

The source model follows the customer journey:

**Marketing Spend → Sessions → Product View → Add to Cart → Begin Checkout → Purchase → Revenue**

```text
marketing_spend
    │ date + campaign
    ▼
sessions
    │ session_id
    ├──────────────► funnel_events
    │
    └──────────────► orders
                        │
                        ├────────► customers
                        │
                        └────────► order_lines
                                      │ sku
                                      ▼
                                  variants
                                      │
                                      ▼
                                  products
```

| Table | Grain |
|---|---|
| `sessions` | One row per session |
| `funnel_events` | One row per funnel event |
| `behavioral_pageviews` | One row per pageview per session timestamp |
| `orders` | One row per order |
| `order_lines` | One row per order line |
| `customers` | One row per customer |
| `marketing_spend` | One row per date × campaign |
| `product_master` | One row per product |
| `variant_master` | One row per variant / SKU |

Grain is treated as an analytical contract. Metrics are calculated only after identifying the appropriate denominator and aggregation level.

## 4. Metric Definitions

Funnel metrics use **distinct sessions**, not raw event-row counts.

| Metric | Definition |
|---|---|
| Session → PDP | Sessions with a Product Detail Page view / Total sessions |
| PDP → Add to Cart | Sessions with Add to Cart / Sessions with PDP view |
| Session → Add to Cart | Sessions with Add to Cart / Total sessions |
| Add to Cart → Checkout | Sessions with Begin Checkout / Sessions with Add to Cart |
| Checkout → Purchase | Sessions with Purchase / Sessions with Begin Checkout |
| Conversion Rate | Purchase sessions / Total sessions |
| Average Order Value | Revenue / Orders |
| Bounce Rate | One-pageview sessions / Total sessions within the comparison group |
| Pages / Session | Total pageviews / Sessions within the comparison group |

A `product_view` means the visitor entered a **Product Detail Page (PDP)**. Seeing a product card on a Homepage or Collection Page does **not** count as a Product View.

Rates are not treated as additive measures. When aggregating across segments or time, rates should be recomputed from their numerator and denominator rather than averaged blindly.

## 5. Simulation and Calibration

The final 90-day scenario contains:

| Measure | Case Volume |
|---|---:|
| Sessions | 1,500 |
| PDP sessions | 600 |
| Add to Cart sessions | 30 |
| Begin Checkout sessions | 18 |
| Purchase sessions | 12 |
| Store CVR | 0.8% |
| Revenue | $271 |
| Paid media spend | $1,050 |

Monthly traffic grows from **250 → 500 → 750 sessions**, while conversion remains weak. This creates the business symptom: acquisition activity is increasing, but order volume remains low.

External ecommerce benchmarks were used only as **calibration and orientation**, not as targets that the synthetic dataset had to reproduce exactly. Comparisons are made only when metric definitions and denominators are aligned.

## 6. Analytical Guardrails

### WHERE is not WHY

A weak metric identifies a location in the customer journey. It does not automatically identify the cause. Low Session → Add to Cart does not prove a pricing problem; 60% No-PDP sessions does not prove visitors never saw products; Collection exits do not prove product-card design is the cause.

### Hypotheses must be testable

Device friction, low visitor intent, weak merchandising, product imagery, pricing, or CTA clarity remain hypotheses until supported by evidence.

### Unsupported explanations can be rejected

Mobile and desktop Session → Add to Cart rates were nearly identical, so device was not supported as the primary explanation.

No-PDP and Reached-PDP bounce rates were approximately **43% vs 42%**, and many No-PDP visitors continued browsing Homepage and Collection pages. The simple early-disengagement explanation was therefore not supported.

### Small samples limit segmentation

With only 12 purchases, the case avoids over-segmenting transaction outcomes or presenting unstable slices as reliable conclusions.

## 7. Data Volume vs. Data Sufficiency

**Data Volume** asks whether there are enough observations to estimate a pattern reliably.

**Data Sufficiency** asks whether the dataset contains the fields and events required to answer the business question at all.

Additional rows alone would not explain *why* a shopper viewed a Collection Page but did not click into a product if product-card exposure and click events were never measured.

This distinction drove the final recommendation to instrument:

**Collection View → Product Card Impression → Product Card Click → PDP View**

before making a causal claim about imagery, pricing, merchandising, CTA clarity, or mobile presentation.

## 8. Evidence Boundary and Decision Rule

The final analysis localized the next decision point:

- 900 of 1,500 sessions did not reach a PDP.
- Many No-PDP visitors continued browsing rather than immediately bouncing.
- 553 No-PDP sessions visited a Collection Page.
- 329 of those sessions ended on Collection.
- **59.5% of Collection-visiting No-PDP sessions stopped there.**

This supports prioritizing **Collection → PDP engagement** as the next measurement and optimization area.

It does **not** establish that the friction is caused by product imagery, price or promotion visibility, product-card information, merchandising, CTA clarity, mobile layout, or visitor intent. Those remain hypotheses for subsequent measurement or experimentation.

## 9. Existing Platform Capability Before New Instrumentation

Before recommending additional tracking, the project reviewed what Shopify already provides through native analytics, including landing-page analysis and several engagement measures.

This led to a production principle:

> **Source Data Availability ≠ Analytical Dataset Availability ≠ Data Sufficiency**

A platform may already capture useful information even when the current analytical dataset does not contain it. Before building new instrumentation, first determine whether the required signal already exists and can be integrated.

BigQuery remains useful as the merchant-controlled environment for combining and analyzing multiple source domains; it does not replace the need to understand native platform capabilities.

## 10. AI-Assisted Analytical Workflow

Because ecommerce was a new domain for this case, AI was used as an analytical copilot to accelerate domain exploration, plausible diagnostic paths, SQL drafting and iteration, validation checks, hypothesis generation, and documentation refinement.

Analytical ownership remained human: business framing, metric and denominator definitions, source and grain decisions, benchmark comparability, evidence thresholds, hypothesis rejection, recognition of data-sufficiency limitations, and the final decision about what to measure next.

The intended workflow is:

**Business framing → AI-assisted exploration → SQL / validation → Human evidence judgment → Decision**
